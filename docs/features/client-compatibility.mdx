## At a glance

- MCPHub's OAuth flow has been **tested end to end with six client stacks**: the official TypeScript and Python MCP SDKs, the Vercel AI SDK, MCP Inspector (CLI), the OpenAI Agents SDK and `langchain-mcp-adapters`. Every one passed all five steps below, under every registration method it supports.
- **Four hosted or local clients were also tried by hand against the production deployment**: Claude on the web, Claude Code, ChatGPT and Codex. Production ran `v2.5.0` for the first part of the session and `v2.5.1` from 01:45 UTC on 2026-11-19, so each row names its version. Claude Code passed all five steps (login, list and call on `v2.5.0`, refresh on `v2.5.1`). ChatGPT (on `v2.5.1`) connects, lists tools and calls one, but its token refresh has not been confirmed. For Claude web only one tool call was made this round; registration, discovery and login come from an earlier connection and were not re-tested. Codex registered and logged in on `v2.5.0`, but it could not call a model on the test machine, so list, call and refresh were not tried. See [Live results](#live-results-against-production).
- **Everything else has not been verified.** That covers the Claude desktop app, Cursor, VS Code, the Anthropic API MCP connector and the OpenAI Responses API remote MCP tool. They need a public HTTPS URL and an account, so the automated harness cannot drive them. See [Not yet verified](#not-yet-verified). Nothing on this page claims that they work.
- The harness results were recorded on **2026-11-18**, the live production results on **2026-11-19 UTC** (the evening of 2026-11-18 in US time). The versions are listed exactly; a newer client release may behave differently.

## What was tested

The tests use the compatibility harness in the repository ([`scripts/compat/README.md`](https://github.com/KazuhaHub/mcphub/blob/main/scripts/compat/README.md)). It starts a throwaway MCPHub with the OAuth server enabled, then drives a real client library through the whole flow against the hub's `/mcp` endpoint. A recording proxy sits between client and hub, so each result is checked against what was on the wire rather than only what the client reported.

Every client performs the same five steps:

| Step | What is checked |
| --- | --- |
| 1. Discovery | The client got through the `401` challenge, the protected resource metadata and the authorization server metadata to the authorization endpoint. |
| 2. OAuth login | Client identification (see below), then authorization code with PKCE, user login and consent, and code exchange. |
| 3. List tools | `tools/list` with the issued access token. |
| 4. Call a tool | `tools/call` on an upstream test tool. |
| 5. Token refresh | Wait until the access token has expired (6 seconds in the harness), then call again. It passes only if the call works, the token was replaced, a `refresh_token` grant was answered `200` on the wire, and the user was not sent through consent a second time. |

Two ways for a client to identify itself were exercised:

- **Dynamic Client Registration (DCR)**: the client calls `POST /oauth/register` first. This is each client's normal behavior.
- **Client ID Metadata Documents (CIMD)**: the client uses an HTTPS URL as its `client_id`. Where a client has a CIMD option it was tested twice: once letting the client decide from the advertised `client_id_metadata_document_supported` flag, and once supplying the URL as pre-registered information, which bypasses that flag and exercises MCPHub's CIMD handling on its own.

The test also records which MCP protocol version each client negotiated.

### What these results do and do not show

They show that the protocol flow works with these client libraries. They do not show that any particular product built on a library works, because products add their own OAuth code, redirect handling and restrictions.

Known differences from a real deployment:

- The hub listens on `127.0.0.1` over plain HTTP. Hosted clients require public HTTPS.
- The login and consent step is automated: the harness signs in as a test user and calls the same two endpoints the consent page calls. Server-side authentication is not relaxed.
- The access token lifetime is 6 seconds, to make step 5 quick. The default is one hour.
- The upstream is a single in-process `echo` tool.
- The build under test is MCPHub `v2.4.1` plus four later commits on `main` (`3f36f05c`), with only documentation and harness changes on top. CIMD was left at its default (on); the harness does not enable it explicitly.

### Run it yourself

```bash
npm install --prefix scripts/compat
pnpm compat --out /tmp/compat-results.json
```

Setup for the Python runners, the options, and how to read the matrix are in the [harness README](https://github.com/KazuhaHub/mcphub/blob/main/scripts/compat/README.md). `node scripts/compat/probe.mjs https://hub.example.com/mcp` runs only the client-independent discovery probe against any hub.

## Live results against production

These runs were done by hand on **2026-11-19 UTC** against the production MCPHub, with the default access token lifetime of one hour. They use real client products, a real identity provider login and the public HTTPS URL, which the harness above cannot do. Production was not one version throughout: it ran `v2.5.0` until `v2.5.1` went live at 01:45 UTC, so the version of each result is given.

| Client | Client version | MCPHub version | Registration | Discovery | OAuth login | List tools | Call a tool | Token refresh |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Claude web (custom connector) | not recorded | `v2.5.0` | DCR (from an earlier connection, not re-tested) | Not re-tested | Not re-tested | Not re-tested | Pass (one call, 01:07 UTC) | Earlier evidence only, see below |
| Claude Code | 2.1.327 | `v2.5.0`, then `v2.5.1` | CIMD | Pass | Pass | Pass (20 tools) | Pass | Pass (`v2.5.1`) |
| ChatGPT (personal Plus account, connector) | not recorded | `v2.5.1` | CIMD | Pass | Pass | Pass (20 tools) | Pass | **Not confirmed** |
| Codex (command line) | 0.142.2 | `v2.5.0` | DCR | Pass | Pass | Not tried | Not tried | Not tried |

How each result was established (all times are UTC on 2026-11-19 unless a date is given):

- **Claude web.** Registration, discovery and login were **not exercised in this round**. They come from a connection made on 2026-10-28 on an older build, whose grant the hub still holds. The only result from 2026-11-19 is one tool call at 01:07, made through the user's existing claude.ai connector (not by going through the Claude web interface by hand). The hub's token table also shows that grant's tokens still being refreshed on 2026-11-18, which suggests Claude web refreshes without sending the user through consent again; that is evidence from an earlier build, not a test of this release.
- **Claude Code** (`v2.5.0` for login, list and call between 01:16 and 01:19; `v2.5.1` for the refresh). Claude Code identified itself with the Client ID Metadata Document `https://claude.ai/oauth/claude-code-client-metadata`, and the consent page named it. Its access token expired at 02:18. A tool call at 02:49, about half an hour after expiry and on `v2.5.1`, worked without a new login, and the hub's record showed a new token with a new expiry of 03:49. The token issued on `v2.5.0` was therefore refreshed by `v2.5.1`.
- **ChatGPT** (`v2.5.1`). The first attempt, on `v2.5.0`, was refused with `Client not found`: ChatGPT's client metadata document prefers `private_key_jwt` and also lists `none`, and MCPHub rejected it. Pull request #36 fixed this and shipped in `v2.5.1`. After that, ChatGPT connected from 01:46 (the consent page read "ChatGPT, requested by chatgpt.com"), listed 20 tools and called one. Its token expired at 02:46, but no further call was made from ChatGPT after that, so whether it refreshes is **unknown**, not failed.
- **Codex** (`v2.5.0`, around 01:19 to 01:20). `codex mcp add` registered it through DCR and `codex mcp login` completed the OAuth login. Codex could not call any model on the test machine (the configured model was not available to the account, and no other model worked), so no tool was listed or called. This is not an MCPHub failure, but it is also not a pass: Codex is **not verified** beyond registration and login.

Not run in this round: the Claude desktop app, Cursor, VS Code, and the Anthropic and OpenAI API remote MCP tools.

### Tokens for an external resource

From a Rackbook end-to-end run on 2026-11-18: an access token that MCPHub issued for an [external resource](/features/oauth) was accepted by Rackbook acting as the resource server. Rackbook verified the token itself against MCPHub's published keys. This was reported by the Rackbook side of the test and was not part of the production client runs above.

The same run found that client registration refused scopes that belong to an external resource. Pull request #37 fixed that. It was merged after `v2.5.1`, so it is not in that release.

## What MCPHub implements

When MCPHub is the authorization server and resource server for its own `/mcp` and `/sse` endpoints, it implements the following. Each item was checked against the code, and the discovery items are also covered by the probe above.

| Feature | Specification | Behavior |
| --- | --- | --- |
| Protected resource metadata | [RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728) | Served at `/.well-known/oauth-protected-resource/<path>` for each MCP and SSE route, with a root fallback. It names the authorization server and the scopes. |
| Authorization server metadata | [RFC 8414](https://datatracker.ietf.org/doc/html/rfc8414) | Served at `/.well-known/oauth-authorization-server`, plus the path-inserted form when the public base URL has a path. OpenID Connect discovery is not served (MCPHub issues no `id_token`); such requests get a JSON `404`. |
| `401` challenge | [RFC 6750](https://datatracker.ietf.org/doc/html/rfc6750) and RFC 9728 section 5.1 | An unauthenticated or invalid-token request gets `WWW-Authenticate: Bearer` with `resource_metadata` and `scope`. An invalid or expired token carries `error="invalid_token"`, which is what makes a client refresh. |
| Issuer identification | [RFC 9207](https://datatracker.ietf.org/doc/html/rfc9207) | Every authorization response, errors included, carries `iss`, and the metadata sets `authorization_response_iss_parameter_supported`. |
| Authorization code with PKCE | [RFC 7636](https://datatracker.ietf.org/doc/html/rfc7636) | Only `S256` is supported. Public clients must use it. |
| Resource indicators | [RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707) | The `resource` parameter is validated; a resource that is not one of MCPHub's own routes is refused with `invalid_target`. |
| Dynamic Client Registration | [RFC 7591](https://datatracker.ietf.org/doc/html/rfc7591) | On by default. Advertised as `registration_endpoint`. |
| Client ID Metadata Documents | [draft-ietf-oauth-client-id-metadata-document](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/) | On by default. Advertised as `client_id_metadata_document_supported`. Fetched with SSRF protection. See [OAuth](/features/oauth#client-id-metadata-documents-cimd). |
| Refresh tokens | [RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749) section 6 | `refresh_token` grant is supported. Defaults: access token one hour, refresh token 14 days. |
| MCP protocol negotiation | [MCP 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) and [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) | Stateless `2026-07-28` requests and session-based `2025-11-25` requests are both accepted on the same endpoint. |

Details and settings are on the [OAuth](/features/oauth) page.

## Not yet verified

The clients below have **not** been fully tested against MCPHub. They need a public HTTPS URL and an account, so the harness cannot run them. Claude web (one tool call only), ChatGPT and Codex have partial results in [Live results](#live-results-against-production); the rest have none. Until someone follows the steps below and records a result, treat anything not marked as passed there as unverified: it may work, it may fail, and this page does not say which.

<Warning>
The vendor-specific details below (menu names, callback hosts, header names) come from general knowledge of public documentation. They were not verified in this repository and vendors change them often. Check the vendor's current documentation. The authoritative redirect URI for any client is the one it actually registers, which the dashboard's OAuth clients page shows.
</Warning>

### Before you start

1. Make the hub reachable over HTTPS and set its public base URL (`install.baseUrl` or `INSTALL_BASE_URL`), so that the issuer, the resource and the `WWW-Authenticate` URL are public addresses.
2. Run the probe against it: `node scripts/compat/probe.mjs https://hub.example.com/mcp`.
3. Set the OAuth access token lifetime to about 60 seconds for the test, and restore it afterwards.
4. Watch the hub's request log (or your reverse proxy's access log) during the test.

Use the global endpoint `https://<public-host>/mcp` (or a group endpoint). What to look for:

| Step | Pass looks like |
| --- | --- |
| 1. Discovery | `POST /mcp` answered `401`, then `GET /.well-known/oauth-protected-resource/mcp`, then `GET /.well-known/oauth-authorization-server`. The client does not stop with a generic "cannot connect". |
| 2. OAuth login | The client registers (`POST /oauth/register`) or sends a URL as `client_id`; the consent page names the right client; after Allow the client reports connected. Note the `redirect_uris` it registered. |
| 3. List tools | The tools you expect appear. An empty list on a connected client points to the token's user or group scope, not to OAuth. |
| 4. Call a tool | A harmless tool, such as an echo or time tool, returns its answer. |
| 5. Refresh | After waiting longer than the token lifetime, one `POST /oauth/token` with `grant_type=refresh_token` is answered `200`, the call works, and there is no second consent screen. |

Also note the protocol version: `initialize` with `2025-11-25`, or `server/discover` and `MCP-Protocol-Version: 2026-07-28`.
